### 2026-11-06 雙機實測回報（0.3.0 (11)）
- 清單**看得到**房間，但從清單加入約 12 秒後失敗；改用手動輸入房主的 **utun4（VPN）位址**＋連接埠＋驗證碼立即成功。
- 推測：公司網路轉送 Bonjour 廣播（所以看得到），但兩台之間直接 TCP 被擋（裝置隔離／不同網段），只有經 VPN 可達。⏳ 待 B 端 `nc` 驗證。
- App 端修正（0.3.0 (12)）：加入改為 8 秒連線逾時並給出正確原因（原本誤顯示「失去連線」）；房主畫面位址逐行顯示並可複製，貼到加入者 IP 欄會自動帶入連接埠。
- 使用者補充：兩台都開著 VPN → 最可能是全通道 VPN 把區網流量導進通道。驗證：B 執行 `route -n get <A 的 en0 位址>`，interface 為 utun 即成立。
- 改進（0.3.0 (13)）：房主在 Bonjour TXT 附上 `addrs`（區網在前、VPN 在後，排除虛擬網卡）與 `port`；加入者先試搜尋到的位址，**每個位址 3 秒**，連不上自動改試下一個；驗證碼錯誤等「有回應的拒絕」不重試。已實測：監聽開始後更新 TXT，搜尋端可收到新內容。

## Phase 0 出口：雙機收聽 10 分鐘

### 準備
1. Mac A（分享）：依 README 建置，或用 `release/LANListen-<版本>-<建置號>.zip`（取最新一個）。
2. Mac B（收聽）：複製 zip 解壓。ad-hoc 簽章，首次開啟會被 Gatekeeper 擋：到「系統設定 → 隱私權與安全性」按「強制打開」。
3. 兩台接同一個 Wi-Fi／有線網段；B 戴耳機。
4. 兩台第一次連線時會跳「區域網路」權限，請允許；A 若跳防火牆「接受連入連線」也請允許。

### （選做）單機預檢
A 上 `open -n LANListen.app` 開第二個實例：一個分享 Chrome、一個收聽 `127.0.0.1`。只能算 🔨，不能算雙機。

### 回歸測試：重複連線／斷線（0.0.1 (3) 起）
2026-11-05 回報：B 連線→離開重複多次後，已顯示未連線仍聽得到聲音，只能關 App。
確定原因：連線物件由畫面持有，切換分頁或角色後 SwiftUI 重建畫面，舊連線沒關、繼續在背景播放。已改由 App 持有，並加上連線編號，避免舊連線的回呼影響新連線。若 B 沒切換畫面也發生，代表另有原因，用下面的診斷數字判斷。

| R2 | B 連線中切到「分享（A）」角色或「擷取測試」分頁再切回 | 仍顯示收聽中、聲音不中斷；按離開後無聲、計數 0 |

### 單機分開聽（0.0.1 (4) 起）
同一台 Mac 跑 A、B 兩個實例時，Chrome 原音與 B 收到的聲音會疊在一起。B 的「輸出裝置」可指定和系統預設不同的裝置：

1. 系統設定 → 聲音 → 輸出：選「MacBook Pro 的揚聲器」（Chrome 從這裡出聲），音量調到 0。
2. A 的「擷取測試」分頁確認：喇叭音量 0 時電平條仍在跳。🎧 2026-11-06 實測：系統輸出音量 0 不影響 ScreenCaptureKit 擷取。
3. B 的「輸出裝置」選「AirPods Pro」，戴上只聽得到 B。
4. 播放中切換 B 的輸出裝置：聲音應短暫中斷後從新裝置出來，不 crash。

限制：AirPods 是藍牙，延遲會比有線耳機大；評估延遲時要註明。

實測（2026-11-06，0.0.1 (4)，單機兩實例，🔨 非雙機）：擷取在喇叭音量 0 時仍有電平、B 經 AirPods Pro 單獨收聽正常、播放中切換輸出裝置正常。
發現：選單出現 `CADefaultDeviceAggregate-<pid>-1`，是 AVAudioEngine 啟動後 Core Audio 為該程序建立的私有聚合裝置。0.0.1 (5) 起排除私有聚合裝置（使用者自建的聚合裝置保留）；以獨立腳本啟動 AVAudioEngine 重現並確認過濾生效。

### 開頭破音
原因推測：WebRTC 接收端緩衝（NetEq）一開始用很小的延遲目標，前幾秒網路抖動造成斷續，之後自動拉大就穩定。此 SDK 沒有開放最小緩衝延遲設定，改為播放端 1.5 秒淡入遮住。
驗證：看 B「補幀：前 10 秒 X%　之後 Y%」。X 明顯高於 Y = 推測成立；Y 也高 = 不只是暖機，需再查（網路／VPN）。
